# dsh-quit 部署记录

## 2026-10-26 18:43 首次安装（v0.1.0）

### 起因

用户要求：「生成一个 dsh 插件，能够不用用户手动关闭 dsh，而是用菜单栏的按钮退出。如果有现成的就用。」

调研结论：

- 社区有现成的 [`knlght/DSH-shutdown`](https://github.com/knlght/DSH-shutdown)（设置页「关机」，`process.exit(0)`）
  与 [`hadesybil-hub/dsh-restart-button`](https://github.com/hadesybil-hub/dsh-restart-button)（重启按钮），
  但都挂在设置页，不符合「菜单栏/侧栏底部按钮」的要求，且不知道 DSHM 的原生停止通道；
- DSHM 的 Host 是 **App 进程内的 node 线程**（`host-ready.json` 的 pid 是 App 进程号，
  `dshm-host.log` 里同时打印 `js-tid`），所以「退出 dsh」只有两条路：写 App 的原生停止通道，
  或直接结束进程；
- Host 启动日志明确打印 `停止通道已就绪：$DSH_HOME/host-stop-request`，与
  `install-queue`、`open-link/*.req`、系统语音桥是同一套文件队列手法（ArkTS 侧
  `EntryAbility` 的启动/重启监视器在轮询）。

用户拍板的方案：

| 决策点 | 用户选择 |
| --- | --- |
| 位置 | 侧边栏底部的用户菜单（落地为 `sidebar.footer.action` + `shell.overlay` 面板） |
| 退出方式 | 两者都做：先写原生停止通道，没退出再强制 `process.exit(0)` |
| 实现基础 | 以现成 `dsh-shutdown` 为底改成本地插件 |
| 附带功能 | 退出 + 重启都要 |

### 交付物（工作区 `DSH插件/dsh-quit/`）

| 文件 | 作用 |
| --- | --- |
| `package.json` | 包声明：`dsh.bundle.patch` + `dsh.client`（inject `@deepseek-ai/dsh-client-ui-sidebar`） |
| `cordis.patch.yml` | bundle patch：只 insert 自己一行，不改官方装载行 |

- 端侧没有外部启动脚本捕获退出码 42，所以「重启」若没被原生通道接管，等于退出后
  需要手动重开应用。
- 强制退出会中断正在进行的 turn（会话日志逐事件落盘，已落盘内容不丢）。

## 2026-10-26 19:1x v0.4.0：回到“直接退出”（不走停止 Host 的通道）

### 再澄清一次需求

用户对 v0.3.0 的反馈：「不是，怎么还是断开核心？」追问后确认：要的是
**点按钮后 App 直接消失、回到桌面**（等同划掉后台），而不是“停 Host、界面留着”的半死状态。
v0.3.0 写的正是 App 的“停止 Host”通道，所以表现就成了用户说的“断开核心”。

物理事实（已在 README 写明）：DSHM 的 dsh 核心 = App 进程内的 node 线程，
**App 退出 ⇔ 核心结束**，不存在“App 退出但核心还活着”的状态。

| 文件 | 改动 |
| --- | --- |
| `lib/index.js` | **删除整个 `host-stop-request` 写入/撤回/遗留清理逻辑**；改为“先把 JSON 响应送回浏览器 → 150 ms 后 `process.exit(0)`”；`/restart` 保留但语义变为“关闭后手动重开”；`/state` 增加 notes 说明；移除 `withdraw` 路由 |

| `check.py` | 必需要素改为 `process.exit(0)` + `EXIT_DELAY_MS`；新增禁止项：代码（非注释）里出现 `host-stop-request` 就报错 |

## 2026-10-26 19:1x v0.4.1：`process.exit(0)` 实测无效，改四级硬退出

### 真机证据（v0.4.0 的失败）

用户点确认后反馈“没有效果”。`$DSH_HOME/dsh-quit.log` 记录：

```
[2026-10-26T11:06:37.113Z] 插件装载：v0.4.0
[2026-10-26T11:06:38.640Z] 路由已注册：/dsh-quit/*
[2026-10-26T11:07:29.108Z] 收到 quit 请求：150ms 后结束进程（pid=46548）
[2026-10-26T11:07:29.266Z] 执行 process.exit(0)：结束 App 进程
```

而 `host-ready.json` 的 `startedAt=11:06:42Z`、`pid=46548` **一直没变**，
之后也没有新的“插件装载”日志 ⇒ **进程没退出、也没重启**。

结论：整条链路（菜单注入 → 面板 → POST → 路由 → 日志）全部正常，
唯一失效的是 `process.exit(0)` —— DSHM 的嵌入 node（libnode in ArkTS）
把这个退出路径吞掉了。

### 本版改动

`lib/index.js` 的退出改为 `tryExit()`，越硬越靠前，逐级写日志：

| 级别 | 手段 | 说明 |
| --- | --- | --- |
| ① | `process.kill(pid, 'SIGKILL')` | SIGKILL 不可捕获/忽略，正常内核下必死 |
| ② | `process.abort()` | 走 libc abort()，立即终止 |
| ③ | `process.exit(0)` | 标准退出（v0.4.0 证明无效，保留作记录） |
| ④ | koffi → `libc.so.6/libc.so/libc.musl-aarch64.so.1` 的 `_exit(0)` | 绕过 Node 退出钩子，直接系统调用 |

每一级的成败都写进 `dsh-quit.log`；四级全失败会写一行
「四级退出手段全部无效：宿主拦截了进程退出，需要 App 侧（ArkTS）提供退出入口」。

### 静态自检

## 2026-10-26 19:2x v0.5.0：重启改成真正的“重启服务”

### 起因

用户反馈：“按重启也是关闭”——v0.4.x 的「重启」和「退出」走的是同一条路（结束进程），
所以重启用不了。

### 关键发现（来自 v0.3.0 留下的真机日志）

早先 v0.3.0 写 `host-stop-request` 时留下了证据：

```
10:49:32  已写原生停止请求：.../host-stop-request
10:49:33  插件卸载：路由与定时器已清理        ← Host 停了
10:50:04  插件装载：v0.1.0                    ← App 把 Host 重新拉起来了
```

说明这条通道的语义就是**“停掉 Host → App 自动拉起”**，App 进程与界面都保留。
这正是“重启 dsh 服务”需要的行为。v0.3.0 拿它当“退出”用，所以用户看到的是
“断开核心、App 还在”；现在把两条路分开。

### 本版改动

| 文件 | 改动 |
| --- | --- |

## 2026-10-26 19:3x v0.6.0：重启 = 重启整个 App（需要 App 侧补丁）

### 澄清

用户进一步明确：「不是让你断开核心，而是重启 APP」——即 **App 关闭后自动重新打开**，
不是“只停 Host、App 还在”。

### 技术判断

插件（Host 侧 node）能结束进程，但 HarmonyOS **没有让应用重启自己的 API**，
插件也无法调用 ArkTS。唯一可行的链路是：

```
插件写 $DSH_HOME/app-restart-request
  → App 侧 RestartBridge（ArkTS）轮询到
  → wantAgent 排一个 START_ABILITY 意图
  → 600ms 后 terminateSelf
  → 系统按意图重新拉起 App
```

所以 v0.6.0 分成两半交付：**插件改动（已完成并部署）+ App 侧补丁（需用户打包）**。
